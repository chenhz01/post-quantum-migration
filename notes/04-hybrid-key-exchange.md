# 后量子密码迁移 · 技术思维 #4：混合密钥交换：X25519MLKEM768 与 RFC 10024

## 两性费曼 · 性二（同行可验证）
- **机制**：混合的安全逻辑是逻辑或——把经典共享秘密与后量子共享秘密合并后送入密钥派生函数生成会话密钥，任一组件安全则组合密钥安全；派生步骤不可省，因为简单拼接会向攻击者泄露长度与分布等结构信息。
- **边界数**：TLS 1.3 混合密钥交换 X25519MLKEM768 由 RFC 10024（2026 年 8 月）标准化 [一手]；IKEv2 的 ML-KEM 草案 -09（2026 年 7 月）在 IESG 审核中未批准 [一手]；英国 NCSC 建议实用选 ML-KEM-768 + ML-DSA-65，并警告生产系统用已发布 RFC 而非变动中的 Internet Draft [二手]。
- **反例**：合并函数实现错误使组合强度退化到较弱组件（设计上是或，实现上可能是与）；或中间盒、企业代理、旧客户端不支持混合组导致协商静默回退纯经典——混合在配置里开着、在流量里死着。
- **可复现**：对任一 TLS 1.3 端点抓一次完整握手，读协商阶段实际选中的密钥交换组；再审计所用实现库中两个共享秘密的合并与派生代码路径。正文给出四条证伪条件。

## 一句话（费曼层）
过渡期不赌大小——经典锁和后量子锁同时锁门，撬开任意一把，另一把还顶着；这就是混合密钥交换。

## 为什么这条路线被低估
讨论的焦点常落在「全面 PQC 何时到来」，工程现实却是「混合部署已是当下」。混合听起来像半成品——两个算法拼一起，不够纯粹——于是常被当成权宜之计而非正式机制。但混合恰恰是标准体系给出的过渡机制，而且已经落地成 RFC：TLS 1.3 混合密钥交换 X25519MLKEM768 由 RFC 10024（2026 年 8 月）标准化。对比同期的另一条线：IKEv2 的 ML-KEM 草案 -09（2026 年 7 月）还在 IESG 审核中未批准。一个已可上生产，一个仍在变动——两条线的状态差，就是一人公司该把工程精力放哪里的直接答案。

## 第一性原理拆解
推到基座：混合的安全逻辑是逻辑或的组合。把经典共享秘密（X25519 的输出）与后量子共享秘密（ML-KEM-768 的输出）合并，送入密钥派生函数，生成会话密钥。只要任一组件安全，组合密钥就安全。这同时覆盖两种失败模式：

- 经典算法被 CRQC 破（Shor 路线）——后量子组件顶着；
- 后量子算法有未发现的设计缺陷——经典组件顶着。

单押任何一边，都是把全部筹码押在单一数学假设上；混合是风险对冲的工程表达。事实包的定性一句话到位：混合是过渡机制不是终点。终局是全后量子，混合是当前阶段的最优解——别把混合当交差，它只是风险曲线上当前最优的一点。

合并的具体方式决定混合的真实强度：两个共享秘密不能简单拼接了事，必须经设计后送入密钥派生函数——拼接本身可能向攻击者泄露结构信息（例如某一段的长度、分布特征），派生函数的作用是把两个来源不同的秘密抹成一段无结构的会话密钥。这解释了一个工程细节：升级到混合密钥交换不是「多支持一个组」的配置动作，而是握手消息变长、派生路径变复杂——集成摩擦（事实包：密钥尺寸不同、协议可能需改参数、真实负载下测集成）正从这些地方长出来。

工程落地的两个判据来自英国 NCSC 的建议：实用选 ML-KEM-768 + ML-DSA-65；并警告生产系统用已发布 RFC 而非变动中的 Internet Draft。后一条对一人公司尤其重要：善伦没有安全团队做 Draft 跟踪，纪律就是护甲——RFC 10024 覆盖的 TLS 侧可以推进，IKEv2 侧等 RFC 再上生产。

## 技术机制与关键事实
- 混合机制：经典+后量子同时用，任一不破即安全（事实包）。
- TLS 1.3 混合 X25519MLKEM768 已由 RFC 10024（2026 年 8 月）标准化（事实包）。
- IKEv2 的 ML-KEM 草案 -09（2026 年 7 月）在 IESG 审核中未批准（事实包）。
- 英国 NCSC 建议实用选 ML-KEM-768 + ML-DSA-65；警告生产系统用已发布 RFC 而非变动中的 Internet Draft（事实包）。
- 混合是过渡机制不是终点（事实包）。
- 集成摩擦：PQC 密钥尺寸不同、握手消息可能需改参数，要在真实负载下测（事实包）。

## 反例与证伪条件
什么证据能证明这条思路错：

1. 合并函数实现错误：两个共享秘密如何拼接、过什么 KDF，实现层的 bug 可以让组合强度退化到较弱组件——「设计上是或，实现上可能是与」。证伪条件：审计主流实现的合并代码路径，或关注后续 CV 修正。
2. 协商剥离：中间盒、企业代理、旧客户端不支持混合组，协商静默回退纯经典——混合在配置里开着，在流量里死着。这条连接 06 号工件的 visibility gap：混合是否真在跑，只能看实际协商结果。
3. 理论层极小概率：两个组件共享某种未发现的联合缺陷，混合价值下降——无现实证据，列为理论风险即可。
4. 性能代价：混合握手更大更慢。对高并发站点，成本要在真实交易负载下测（事实包），不能只看握手成功与否。

## 对善伦业务的迁移点
- 独立站 TLS：优先确认自己用的 CDN 与源站是否在协商组里暴露 X25519MLKEM768——RFC 10024 已标准化，这是当前唯一「已发布、可上生产」的混合部署位，优先级高于一切。
- 远程访问 / VPN：IKEv2 侧 ML-KEM 仍是草案 -09 未批准状态，按 NCSC 警告等 RFC——这一步的正确动作是「记录等待」，不是焦虑。
- 支付通道 API 的服务端到服务端长连接：能否混合取决于对方支持，按 06 号方法实测协商结果，把结果写进供应商评估。
- 对齐正明 AI 系统：内部节点间通信两端自控，是最先能做到强制混合的场景。
